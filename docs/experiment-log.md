# Experiment log

Format per experiment: **Question → Method → Result (table) → Findings (root cause /
trade-off) → Learned**. Every number below is copied from a run's report under
`runs/<run>/` or from `results/*.csv` generated by `scripts/summarize.py`.
Unresolved problems are listed too.

## E0 — Tool/option verification for Phase 2 (installed version)

**Question.** Which of the requested CTS knobs exist in the installed
OpenROAD (ORFS submodule `98c6045c72b7`), and what does the ORFS default flow
already turn on?

**Method.**
1. Read `src/cts/README.md` and `src/cts/src/TritonCTS.tcl` at exactly that
   commit (sparse checkout of the OpenROAD repo).
2. `help clock_tree_synthesis` / `help set_cts_config` in the installed binary.
   The output is identical to the README signature.
3. Ran `clock_tree_synthesis -balance_levels` in the binary to see what it does.
4. Read ORFS `flow/scripts/cts.tcl` to see the arguments it passes.
5. Inspected the CTS database of the baseline run with `scripts/ndr_check.tcl`.

**Result.**

| Option | Available? | Evidence / behaviour in this version |
|---|---|---|
| `-sink_clustering_enable` | **Yes**, and **ORFS passes it by default** | `cts.tcl`: `set cts_args [list -sink_clustering_enable -repair_clock_nets]`. Baseline log: `CTS-0206 Best clustering solution was found from max clustering size of 9 and max clustering diameter of 56` (clk_i_regs) / `72` (gated clk). |
| sink cluster size / diameter | **Yes**: `-sink_clustering_size`, `-sink_clustering_max_diameter` (ORFS vars `CTS_CLUSTER_SIZE`, `CTS_CLUSTER_DIAMETER`) | If unset, both are auto-selected under a capacitance limit (sink-buffer input cap × 10). The internal cap is 30 sinks. |
| `-sink_clustering_levels` | Yes | Not used. |
| `-balance_levels` | **Accepted but obsolete** | `TritonCTS.tcl:460` only prints `[WARNING CTS-0132] -balance_levels is obsolete.` Confirmed in the binary. It has no effect, so it is **not** an experiment variable. |
| `-apply_ndr <none\|root_only\|half\|full>` | **Yes** (both `clock_tree_synthesis` and `set_cts_config`) | 2× spacing NDR on non-leaf clock nets. **Default is `half`** (`CtsOptions.h: ndrStrategy_ = NdrStrategy::HALF`). The baseline database has rule `CTS_NDR_0` on **7 / 318** clock nets, so **NDR is already on in the default flow**. |
| Useful skew | **No built-in feature** | No useful-skew / skew-scheduling option in `cts` or in `repair_timing` (searched README and Tcl). TritonCTS targets zero skew. `-delay_buffer_derate` and `-no_insertion_delay` only concern macro/register latency balancing. |
| `set_clock_latency` on pins (for manual skew) | Yes (OpenSTA) | OpenSTA docs: *"set_clock_latency removes propagated clock properties for the clocks and pins objects"*. A pin with a latency override becomes an ideal-clock pin with that arrival. That makes it an **STA what-if**, not a physical change. |
| `-obstruction_aware`, `-repair_clock_nets`, `-dont_use_dummy_load`, `-sink_buffer_max_cap_derate`, `-distance_between_buffers` | Yes | Not varied. Kept at ORFS defaults (`-repair_clock_nets` on). |

Library constraint discovered here: the only clock buffers are `CLKBUF_X1/X2/X3`.
TritonCTS uses `CLKBUF_X3` for every buffer, so buffer sizing is not a
lever.

**Findings → consequences for the run matrix.**

* The ORFS default already includes sink clustering **and** NDR `half`. The
  requested "RB: turn clustering on" and "RC: turn NDR on" are therefore
  re-expressed as deviations from the default:
  * RB: clustering **off**, plus explicit cluster sizes smaller and larger
    than the auto-chosen 9.
  * RC: NDR **none** and NDR **full**, bracketing the default `half`.
* `-balance_levels` dropped (obsolete, no-op).
* RD uses SDC `set_clock_latency` overrides (`scripts/rd_useful_skew.tcl`).

**Learned.** Check what the "default" really contains before designing
on/off experiments. Here two of the three planned "turn X on" experiments
were already on.

**Unresolved / issue found while preparing RD.** In the first RD test,
OpenSTA's pin property `arrival_max_rise` on some register CK pins changed
from 0.291 ns to **1.745 ns** after `find_timing_paths` had run. The overrides
were wrong as a result (test hold WNS −1.30 ns). The fix was to sample all CK
arrivals *before* path enumeration and to add a sanity range check. After the
fix: 118 overrides with latencies of 0.288–0.299 ns, hold WNS +0.09 ns. I did
not determine why the property changes. It looks like a side effect of
OpenSTA path enumeration on the search state, and it is worth reporting
upstream.

## E1 — Phase 1 clock-period sweep (find the stress period)

**Question.** What is the shortest period Ibex closes at after detailed
route and RC extraction? Which period fails by the smallest margin (the
"stress period") and should be used for the CTS comparison?

**Method.** Full ORFS flow per period, all other settings at the ORFS default
(50 % utilization, default CTS). `scripts/sweep_period.sh 1.8 2.0 2.2 2.3 2.4 2.6`,
plus 2.25 added afterwards to locate the boundary. "Closes" means
post-route setup WNS ≥ 0 **and** hold WNS ≥ 0 **and** 0 DRC. The post-route
numbers come from OpenSTA with the OpenRCX SPEF (`6_final.spef`).
Data: `results/period_sweep.csv`, plot: `results/period_sweep_wns.png`.

**Result.**

\*Two runs in parallel on 4 vCPUs (2.25 ran three-way), so wall time is not a
clean per-run runtime. The single baseline run took about 515 s.

* **Shortest closing period: 2.25 ns** (≈ 444 MHz).
* **Stress period: 2.2 ns** (≈ 455 MHz, the ORFS default). It misses by
  14 ps, with 31 failing endpoints and TNS −0.36 ns. Used for Phase 2.
* Reproducibility: the 2.2 ns sweep point `P2p2` and the Step 0 run
  `step0_default` were launched separately, one alone and one in parallel
  with another run. They are **identical** in every reported metric (WNS,
  TNS, wirelength, power). The flow is deterministic on this setup.

**Findings.**

1. **The failure at 2.0–2.2 ns comes from the gap between the global-route
   RC estimate and OpenRCX.** At 2.0 ns `repair_timing` drives the
   GRT-stage WNS to −0.00004 ns. At 2.2 ns GRT says +0.016 ns. In both cases
   OpenRCX then lowers it by about 20–30 ps (−0.020 and −0.014 ns). The
   design is not limited by logic depth in this range. It is limited by the
   difference between the RC model the optimizer sees and the extracted RC.
   That is why WNS is almost flat between 2.0 and 2.2 ns while TNS changes
   by 7.6×.
2. Below 2.0 ns the optimizer can no longer keep up. At 1.8 ns it inserts 92
   setup buffers, grows cell area by 12 % and power by 26 % relative to
   2.2 ns, and still ends at WNS −0.216 ns with 1580 failing endpoints.
3. The WNS curve is **not monotonic**: 2.4 ns has less post-CTS slack
   (+0.016) than 2.3 ns (+0.079). Synthesis (ABC with `-constr` derived from
   the period) and placement both change with the period, so each period is
   effectively a different netlist and placement. Differences of about
   10–20 ps between neighbouring periods are within this "implementation
   noise" and do not reflect a physical trend.
4. The clock tree is essentially the same at every period: 316–321
   `CLKBUF_X3`, max insertion delay 0.303–0.309 ns. The clock tree does not
   adapt to the period. The data path does.

**Learned.** With a deterministic flow, run-to-run noise at a *fixed* setup
is zero. The relevant noise for Phase 2 is the sensitivity of the result to
small perturbations (finding 3), which is about ±20 ps here. A CTS strategy
that changes post-route WNS by less than about 10–20 ps should not be called
"better".

## E2 — Phase 2 setup and reproducibility (R0a, R0b, RA)

**Question.** Is the comparison clean? Does anything other than the CTS
setting change between runs, and how large is the run-to-run noise?

**Method.** At the stress period 2.2 ns:
* **R0a** and **R0b**: two independent full flows (synthesis → finish).
* **RA**: copy R0a, delete everything from stage 4 on, re-run CTS → finish
  (`run.sh -b R0a`). All other variants use the same mechanism. Their
  `3_place.odb` is byte-identical to R0a's (checked with `cmp`), and their
  `flow.log` shows no synthesis/floorplan/place step.

**Result.** R0a, R0b and RA are identical in **every** metric of
`results/cts_comparison_full.csv`: WNS −0.0143 / TNS −0.3602 ns, skew
0.0397 ns, 316 clock buffers, 256 598 µm wire, 118 073 vias, 12.706 mW.
(The step0 run and P2p2 from E1 match them too.)

**Findings.** The flow is fully deterministic on this machine and image:
same inputs give bit-identical outputs, even with two runs sharing the CPU.
So **the R0a/R0b noise estimate is 0**. That estimate is misleading,
though. It only says that *repeating* a run is free of noise. It says
nothing about how much the result moves when *anything* is perturbed.
That was measured separately (E5).

**Learned.** "Run it twice" is a necessary check, but a deterministic tool
makes it uninformative. A perturbation experiment is needed to get a
usable noise floor.

## E3 — Sink clustering (RB_nocl, RB_s4, RB_s20 vs RA)

**Question.** The ORFS default already enables sink clustering, with the
size auto-selected. What happens with clustering **off**, with **smaller**
clusters (4) and with **larger** clusters (20)?

**Method.** Branch from R0a. Only `CTS_ARGS` / `CTS_CLUSTER_SIZE` differ.
* RB_nocl: `-repair_clock_nets`, no `-sink_clustering_enable`. NDR stays at
  the default `half`.
* RB_s4 / RB_s20: default arguments plus `-sink_clustering_size 4 / 20`.
  The diameter stays automatic.

**Result** (post-route, OpenRCX; worst-path decomposition from
`scripts/worst_paths.tcl`).

| metric | RA (auto, size 9) | RB_nocl (off) | RB_s4 | RB_s20 |
|---|---|---|---|---|
| tree (CTS log) | 4 H-tree levels + 277 leaf-cluster buffers, path depth 2–3 | 7 H-tree levels, 0 leaf buffers, depth 3–3 | 5 levels + 487 leaf buffers, depth 3–4 | **identical to RA** |
| clock buffers / dummy loads | 316 / 232 | 295 / 221 | **590** / 110 | 316 / 232 |
| insertion delay min / max (ns) | 0.2723 / 0.3122 | 0.2667 / **0.2886** | 0.2823 / 0.3124 | = RA |
| setup skew (ns) | 0.0397 | **0.0217** | −0.0298 | = RA |
| clock wirelength (µm) | 12 636 | 12 194 | 14 382 | = RA |
| setup WNS post-CTS / post-GRT (ns) | +0.040 / +0.016 | +0.053 / +0.023 | +0.045 / +0.011 | = RA |
| **setup WNS / TNS post-route (ns)** | −0.0143 / −0.360 | **+0.0043 / 0** | **+0.0102 / 0** | = RA |
| worst path: launch / capture CK (ns) | 0.3053 / 0.2841 | 0.2778 / 0.2741 | 0.3049 / 0.2837 | = RA |
| worst path: capture − launch (ns) | −0.0212 | **−0.0037** | −0.0212 | = RA |
| worst path: data delay (ns) | 2.1559 | 2.1566 | **2.1302** | = RA |
| hold WNS (ns) / hold buffers | +0.0855 / 0 | +0.0853 / 0 | +0.0848 / 0 | = RA |
| clock power / total (mW) | 4.158 / 12.706 | 4.245 / 12.795 | **5.239 / 13.782** | = RA |
| cell area (µm²) | 29 018 | 29 008 | 29 281 | = RA |
| GRT usage total / overflow | 28.60 % / 0 | 28.91 % / 0 | 29.06 % / 0 | = RA |

**Findings.**
1. **RB_s20 is a no-op.** Its `4_1_cts.odb` is byte-identical to RA's. When
   no size is given, clusters are limited by capacitance (sink-buffer input
   cap × 10). With `CLKBUF_X3` sinks that limit is reached at about 9 sinks,
   so a cap of 20 never binds. Larger clusters need a bigger sink buffer,
   and Nangate45 has nothing above `CLKBUF_X3`.
2. **Clustering off (RB_nocl) is a real clock-tree improvement.** All
   critical paths go from the IF-stage instruction register
   `if_stage_i.instr_rdata_id_o[*]` to register-file flops `rf_reg[*]/D`.
   With clustering on, the launch flop sits in a cluster whose leaf buffer
   arrives late (0.305 ns), while the capture flops arrive early (0.284 ns):
   −21 ps of *harmful* skew. Without pre-clustering, the H-tree is built
   directly to the sinks (7 levels, uniform depth 3). That cuts the max
   latency by 23 ps and the harmful skew on the critical path to −4 ps. The
   +17.5 ps gain is entirely in the clock term (the data delay changed by
   −0.7 ps). Cost: +2.1 % clock power even with 21 fewer buffers, probably
   because the 7-level trunk carries more switched wire capacitance near the
   root. Exact cause not verified.
3. **RB_s4 closes timing, about half of it through the clock tree.**
   *Corrected in E7.* The first version of this finding said "not a
   clock effect". It looked only at the single worst path, where the skew
   term is unchanged (−21.2 ps) and the whole +24.5 ps gain is in data
   delay (−25.7 ps). Averaged over all 31 endpoints that fail in RA, RB_s4's
   +27.3 ps splits into **+14.6 ps clock** and +12.7 ps data (E7 method).
   The data part is inside the routing-noise band (E5), but the clock part
   is real. 487 extra leaf buffers also force detailed placement to
   re-legalize cells, which is where the data-path change comes from. The
   costs are large: 2× clock buffers, +14 % clock wire, **+26 % clock
   power, +8.5 % total power**, +0.9 % area.

**Learned.** The sign of the CTS effect depends on *which* flops share a
cluster. Clustering balances latency *within* a cluster but can leave
clusters offset from each other by about ±20 ps. With only a few critical
paths, whether that offset helps or hurts them is close to chance. Here it
hurt.

## E4 — Non-default rules (RC_none, RC_root, RC_full vs RA = half)

**Question.** Does NDR (2× spacing on clock nets) matter here, and which
strategy is best?

**Method.** Branch from R0a, default arguments plus `-apply_ndr <s>`. After the run,
`scripts/ndr_check.tcl` counted the clock nets that actually carry
`CTS_NDR_0` in `6_final.odb`.

**Result.**

| metric | RC_none | RC_root | **RA (half, default)** | RC_full |
|---|---|---|---|---|
| clock nets with NDR | 0 / 318 | 7 / 318 | 7 / 318 | 9 / 318 |
| CTS database vs RA | NDR differs only | **byte-identical** | – | NDR differs only |
| insertion delay min / max (ns) | 0.2791 / 0.3107 | = RA | 0.2723 / 0.3122 | 0.2712 / **0.2979** |
| setup skew (ns) | 0.0316 | = RA | 0.0397 | **0.0267** |
| **setup WNS / TNS post-route (ns)** | −0.0090 / −0.213 | = RA | −0.0143 / −0.360 | **+0.0164 / 0** |
| worst path capture − launch (ns) | −0.0162 | = RA | −0.0212 | −0.0071 |
| worst path data delay (ns) | 2.1556 | = RA | 2.1559 | 2.1392 |
| clock wirelength (µm) | 12 623 | = RA | 12 636 | 12 599 |
| metal4 GRT usage | 25.23 % | = RA | 25.78 % | 25.78 % |
| clock / total power (mW) | 4.162 / 12.710 | = RA | 4.158 / 12.706 | 4.140 / 12.688 |

**Findings.**
1. **NDR barely reaches the tree.** NDRs are never put on leaf nets, and
   with clustering about 300 of the 318 clock nets *are* leaf nets.
   `half` and `root_only` both cover the same 7 trunk nets, so `root_only`
   = `half`. `full` adds only 2 more nets.
2. Even so, NDR changes timing measurably. The NDR nets are the long,
   upper-level trunk wires. Wider spacing lowers their coupling capacitance,
   which OpenRCX extracts. `full` lowers max latency by 14 ps and improves
   the critical-path skew by 14 ps. `none` improves the skew by 5 ps,
   but through a different tree routing (min latency +7 ps), so the effect
   is not monotonic.
3. RC_full's total gain (+30.7 ps) is about half clock (+14 ps) and half data
   path (+17 ps). The data half is inside the routing-perturbation band
   (E5). Only the clock half can be credited to NDR.
4. Cost of NDR: negligible here. The clock wire is only 4.9 % of the
   256 600 µm total, and only a few nets carry the rule. Routing usage
   changes by ±0.3 % or less, overflow is 0, and power is unchanged.
5. OpenSTA does **no crosstalk / SI analysis**, so the main real-world
   benefit of clock NDR (less aggressor-induced delta delay and jitter)
   is invisible in this flow. Only the reduced grounded-equivalent
   capacitance is seen.

**Learned.** Check which nets a strategy actually touches before reading
anything into a strategy name. "full" sounded like the whole tree, but in
practice it meant 9 nets.

## E5 — Routing-perturbation noise floor (N_gr48, N_gr52)

**Question.** E2 showed zero repeat noise. How much does post-route WNS move
when the *routing* changes slightly but the clock tree does not?

**Method.** Branch from R0a with the default CTS (so the clock tree is
byte-identical to RA). A `PRE_GLOBAL_ROUTE_TCL` hook (`scripts/noise_grt_adj_*.tcl`)
changes the metal2–metal3 global-routing capacity adjustment from 0.50 to
0.48 / 0.52. Nothing else changes.

*First attempt failed:* overriding `FASTROUTE_TCL` had no effect. ORFS
applies it in `floorplan.tcl` and stores it in the ODB, so runs that branch
at CTS never re-read it. I noticed because the congestion table was
identical to RA's. The hook-based version was checked through its log
line `FLW-0911`.

**Result.**

| metric | RA | N_gr48 | N_gr52 |
|---|---|---|---|
| metal2 GRT usage | 56.56 % | 56.48 % | 56.99 % |
| vias / wire (µm) | 118 073 / 256 598 | 117 911 / 256 584 | 118 489 / 256 524 |
| setup skew (ns) | 0.0397 | 0.0390 | 0.0423 |
| worst path capture − launch (ns) | −0.0212 | −0.0206 | −0.0212 |
| worst path data delay (ns) | 2.1559 | 2.1560 | **2.1353** |
| **setup WNS / TNS (ns)** | −0.0143 / −0.360 | −0.0139 / −0.347 | **+0.0063 / 0** |

**Findings.** A routing-only change, with no change to the CTS, moved
post-route WNS by **+0.4 ps and +20.6 ps**, and the second one closed timing. The
movement is all in the **data term**. The critical-path skew term moved by
≤ 0.6 ps. With n = 2 this is a lower bound on the noise, not a
distribution.

Per-endpoint view (added in E7; mean over the 31 endpoints that fail in
RA): N_gr48 Δslack +0.4 ps = clock +0.7 / data −0.3. **N_gr52 Δslack +26.8 ps
= clock −0.9 / data +27.7.** The noise band for the data part is therefore
up to about 28 ps. The clock part stays within 1 ps.

> **Corrected by E14 (10 probes).** The clock part is *not* within 1 ps.
> Global route also re-routes the clock nets, so clock arrivals move by up
> to about 9 ps with an identical tree. The clock-part noise of the
> 31-endpoint split reaches +7.85 ps (sd 3.3 ps over 9 independent probes).
> The consequences listed below are re-judged in E14.

**Learned / consequence for E3–E4.**
* A data-path change of up to about 28 ps is **noise**. The data parts of
  RB_s4 (+12.7) and RC_full (+16.7) are not credited.
* A **clock** change is robust (≤ 0.9 ps of noise in the clock part), so
  RB_nocl (+18.9 ps), RB_s4 (+14.6 ps), RC_full (+13.9 ps) and RC_none
  (+4.6 ps) are real clock-tree effects. These are per-endpoint values, which
  differ slightly from the single worst-path values quoted in E3/E4.
* At a stress period that misses by 14 ps, "does it close?" is decided by
  that noise. The pass/fail column must not be used to rank strategies.

## E6 — RD: useful-skew emulation with `set_clock_latency`

**Question.** No built-in useful skew exists (E0). How much would
deliberately delaying the capture clock of critical registers be worth?

**Method.** `POST_CTS_TCL = scripts/rd_useful_skew.tcl` (after CTS repair,
before writing `4_cts.sdc`):
* Candidates: register endpoints with post-CTS setup slack < T = 60 ps.
* For each one, delta = min(T − s_capture, (s_launch − s_capture)/2,
  hold_slack − 20 ps, 80 ps).
* The CK pin then gets `set_clock_latency (CTS-stage arrival + delta)`.
* The overrides are carried in `4_cts.sdc`, `5_1_grt.sdc` and
  `6_final.sdc`. All three files contain the same 62 overrides, so GRT
  repair and final STA see them.

**Result.** 62 registers received overrides, all in
`gen_regfile_ff.register_file_i`. Delta was 6.9–19.7 ps (mean 13.3 ps).
Physically RD is **identical to RA**: same clock tree, same buffers, vias,
wirelength and power, and no extra hold or setup buffers. In STA:

| metric | RA | RD |
|---|---|---|
| worst-path capture CK (ns) | 0.2841 | 0.3118 |
| worst-path capture − launch (ns) | −0.0212 | **+0.0066** |
| setup WNS / TNS post-route (ns) | −0.0143 / −0.360 | **+0.0139 / 0** |
| hold WNS (ns) | +0.0855 | +0.0855 |

**Findings.**
1. The +28 ps gain is the largest of any variant, and it costs nothing in
   power or area **because nothing was built**. It is an upper bound on
   what a useful-skew tool could get from this one path family.
2. The capture-latency shift on the worst path (+27.7 ps) is larger than
   the delta applied (≤ 19.7 ps). The override freezes the **CTS-stage**
   (placement-RC) arrival, which is about 8 ps higher than the post-route
   extracted latency of those flops. This is a known flaw of pin-latency
   emulation: the overridden pins stop following the real tree.
3. A physical implementation would need about 13–20 ps of extra latency on
   62 register-file flops. In Nangate45 that is roughly one `CLKBUF_X1`
   stage per flop group. Its hold impact on the regfile → regfile paths is
   protected here only through the hold-slack guard. Hold slack is +85 ps at
   the typical corner, so there is room, but that would need checking at a
   fast corner, which this platform does not have.

**Resolved in E7.** RD was not physically built in this experiment. E7
builds it with real delay buffers and re-routes.

## E7 — RD_phys: useful skew built with real delay buffers

**Question.** RD (E6) only emulated useful skew in STA. Does the gain hold
when the extra capture latency is physically built, placed and routed, and
what does it cost?

**Method.** `POST_CTS_TCL = scripts/rd_phys_useful_skew.tcl`, branching from
R0a like every Phase 2 run.

1. **Selection: identical to RD.** Same hook point, same rule, code copied
   verbatim. The same 62 register-file flops were selected, with target
   delta 7–20 ps (mean 13.3 ps).
2. **Group and insert.** The selected CK pins are grouped by the leaf clock
   net that drives them (15 groups of 1–8 flops). Each group is moved
   behind one new buffer with `insert_buffer -buffer_cell CLKBUF_X1
   -load_pins <group CK pins> -location <group centroid>`. The new output
   nets are marked `CLOCK`, and the buffers are legalized with
   `detailed_placement_helper` (419 cell moves, max 3.4 µm).
3. **Measure and guard.** The realised latency is measured from timing paths
   (`target_clk_delay` before vs after, not from the unreliable pin
   property). A buffer is removed again if its delay exceeds what its flops'
   launch and hold constraints allow, min((s_launch − s_cap)/2,
   h_cap − 20 ps, 80 ps). The guard removed none.
4. The flow then continues normally: GRT + repair_timing, detailed route,
   OpenRCX, STA. There is **no** SDC latency override anywhere.
5. **RD_phys_b1**: the same hook with `BUF_X1`, which has a smaller delay
   step (`scripts/rd_phys_useful_skew_bufx1.tcl`).

New analysis scripts:
* `scripts/dump_ck_arrivals.tcl`: the post-route CK arrival of every
  register, sampled before any path enumeration.
* `scripts/endpoint_slack.tcl`: every setup endpoint with slack < 100 ps,
  with its capture latency and startpoint.
* `summarize.py`: the per-endpoint clock/data split over RA's 31 failing
  endpoints, which all start at `if_stage_i.instr_rdata_id_o[20]`. It
  replaces the single-worst-path split, which breaks when the worst
  endpoint moves.

**Result.**

| metric | RA | RD (STA only) | **RD_phys** (CLKBUF_X1) | RD_phys_b1 (BUF_X1) |

**Findings.**
1. **The physical version beats the emulation.** RD_phys gains +36.3 ps of
   clock part on the 31 critical endpoints, against +26.7 ps for RD. That is
   *not* because the physics is better. It is because a single `CLKBUF_X1`
   stage gives about 36 ps where only 13 ps (mean) was requested. The
   requested delta was conservative (capped at T − s_cap), and the launch
   side of these flops had ≥ 0.14 ns of margin, so the overshoot was
   harmless and helpful. Without that margin, the same overshoot would have
   created a new critical path. `BUF_X1` (median 28 ps) lands closer to the
   target and gains less (+28.7 ps).
2. **The bottleneck moves.** In RD_phys the worst endpoint is now
   `rf_reg[444]`, a flop that was *not* selected (its CTS-stage slack was
   above T = 60 ps). Only 3 endpoints remain below 20 ps. Because of this
   endpoint switch, the single-worst-path decomposition became misleading
   (it showed clock −11 ps / data +39 ps). That is why the per-endpoint
   split was introduced.
3. **The skew is real and confined.** The 62 flops really are 27–41 ps later
   post-route (SPEF). All other flops moved by less than 8 ps, from the
   re-legalization and re-routing around the 15 new cells.
4. **Cost is small but not zero.** 15 cells, +0.04 % area, **+0.9 % clock
   power**, +0.3 % total power, +0.5 % clock wire, +11 ps max insertion
   delay. On the timing side, the paths launched *by* the delayed flops lose
   about 34 ps, hidden behind ≥ 0.14 ns of remaining slack. Hold *into* them
   loses 39 ps (0.401 → 0.362 ns). No hold fixing was triggered at the
   single typical corner.
5. `report_clock_skew` now reports −0.057 ns (RD_phys) / −0.049 ns
   (RD_phys_b1). That number is no longer a quality metric, because the skew
   is intentional.

**Learned.**
* An STA latency override is not a reliable predictor of the physical
  result. Here the real delay step is coarser than the request (one cell is
  about 36 ps), and the override also froze CTS-stage latencies.
* In a library this coarse, useful skew is a matter of choosing *which
  flops get one extra stage*, not of dialling in picoseconds.
* Comparing runs by their single worst path breaks as soon as the
  optimization moves the bottleneck. Compare a fixed endpoint set instead.

**Not done / open.**
* Single pass only (done in E8). The selection was not repeated after insertion, so the
  next path family (`rf_reg[444]` …) was not treated.
* No multi-step delay chains or delay-cell sizing.
* No fast-corner hold check, because the platform has no fast corner.

## E8 — Useful skew round 2: treating rf_reg[444] and the next tier

**Question.** After RD_phys, the worst endpoint is `rf_reg[444]` (+18.5 ps),
a flop that round 1 did not select. Does a second round of useful skew
aimed at it improve the design further?

**Starting point (RD_phys post-route).** `rf_reg[444]` is the edge of a
dense tier: 3 endpoints < 20 ps, 54 at 20–30 ps, 121 at 30–40 ps. Almost
all are register-file flops fed from `if_stage_i.instr_rdata_id_o[20]`. The
next endpoint after `rf_reg[444]` is at +18.8 ps, so delaying `rf_reg[444]`
alone can raise WNS by at most 0.3 ps, far below the routing noise (E5).
Round 1 missed it because it selected from CTS-stage (placement-RC) slack,
where `rf_reg[444]` was above T = 60 ps.

**Method.**
1. `scripts/rd2_select.tcl` runs on RD_phys's **routed** database + SPEF
   and selects register endpoints with post-route slack < T2.
   * Guard: allowed = min((s_launch − s_cap)/2, h_cap − 20 ps, 80 ps), and a
     register is kept only if allowed ≥ 45 ps (one `CLKBUF_X1` stage
     realised up to 41 ps in E7).
   * `RD2_STACK=1` also selects round-1 flops that are still < T2. They get a
     second stage behind their round-1 buffer.
2. `scripts/rd_phys2_useful_skew.tcl` (POST_CTS hook, branch from R0a) runs
   round 1 unchanged. It is deterministic and rebuilds the same 15 buffers
   with the same 419 legalization moves. Then it inserts round 2: one
   `CLKBUF_X1` per group of targets sharing a CK net, with the same measure
   and remove guard as round 1. The flow then re-routes from scratch.
3. Two variants:
   * **RD_phys2_444**: literally only `rf_reg[444]` (1 buffer).
   * **RD_phys2**: T2 = 30 ps with stacking: 48 new flops + 9 round-1 flops,
     57 targets, 21 buffers, none removed by the guard. Realised extra
     latency (CTS stage) was +25 to +41 ps, median 36; the stacked second
     stages gave +25 to +30 ps.

**Result** (post-route, OpenRCX; "Δ vs RA on 31" is the per-endpoint metric
from E7).

**Findings.**
1. **Fixing `rf_reg[444]` alone does nothing for the design.** Its own slack
   rises from +18.5 to +47.1 ps; its CK is 28 ps later behind the new
   `CLKBUF_X1`. But WNS *drops* by 1.7 ps (+18.5 → +16.7 ps). The re-route
   moves other endpoints by more than the 0.3 ps that was available. For
   example, round-1 flops `rf_reg[831]`/`[895]` fall from about +22 to
   +17 ps, and `rf_reg[787]` becomes the new worst endpoint. A single-
   endpoint fix on a dense tier is lost in routing noise.
2. **Treating the whole tier works, but with sharply diminishing returns.**
   RD_phys2 lifts the 57 round-2 targets by +38.5 ps on average and leaves
   no endpoint below 20 ps. WNS still only gains **+5.0 ps** (+18.5 →
   +23.5 ps). That compares with +32.8 ps from round 1. The new limiters
   are:
   * `rf_reg[863]`, a round-1 flop that round 2 did not re-treat (its
     RD_phys slack was > 30 ps) and that dropped through routing noise.
   * Two **new path families** from other instruction-register bits:
     `instr_rdata_id_o[15]` → `rf_reg[381]` (+25.2 ps) and
     `instr_rdata_id_o[1]` → `rf_reg[87]` (+26.9 ps).

   Behind them is a wall of 108 endpoints at 30–40 ps. Each further round
   would delay another large group for a few ps.
3. **Cost per round.**
   * Round 1: 15 buffers, +0.9 % clock power, +32.8 ps WNS.
   * Round 2: 21 more buffers, another +1.1 % clock power, +5.0 ps WNS.
   * In total vs RA: +36 buffers, +2.0 % clock power, +0.65 % total power,
     +29 µm² (+0.1 % area). Max insertion delay +40 ps, because of the
     two-stage flops.
   * Timing margins consumed on the 110 delayed flops: launch side −17 ps
     (0.143 → 0.126 ns), hold side −63 ps (0.401 → 0.338 ns). Both still
     have large margins, and no hold fixing was triggered at the typical
     corner.
4. **The limit is the startpoint, not the endpoints.** All three remaining
   families start at instruction-register bits. Delaying hundreds of
   register-file capture flops one group at a time is the expensive side
   of the trade. The natural next step would be the opposite move: make
   the few **launch** flops (`if_stage_i.instr_rdata_id_o[*]`) *earlier*,
   for example by moving them to an upstream clock net. That has to be
   paid for on the paths captured *by* those flops and on their hold.
   It was not tried.

**Learned.**
* Iterative useful skew needs post-route selection. The CTS-stage estimate
  missed `rf_reg[444]`.
* Every round re-routes the whole design, so its WNS benefit must exceed
  the routing noise (≈ 20–28 ps on the data part) to be visible.
  Per-endpoint gains on the treated flops (+28.6 ps for `rf_reg[444]`,
  +38.5 ps mean for the tier) are the reliable measure of what the round
  achieved.

## E9 — RE: useful skew on the launch side ("make the launch flop earlier")

**Question.** All critical paths start at a few instruction-register flops
`if_stage_i.instr_rdata_id_o[*]` and end at hundreds of register-file flops.
Instead of delaying many capture flops (E7/E8), can a few launch flops be made
*earlier*?

**Method.** No cell is added. A launch flop's CK pin is moved from its leaf
clock net to the input net of the leaf `CLKBUF_X3` that drives it
(`disconnect_pin` / `connect_pin`), skipping one buffer stage.

* `scripts/re_select.tcl` picks targets on a **routed** run (SPEF). For each
  candidate flop F:
  * cost side: setup slack of paths captured *by* F (s_cap), and hold slack
    of paths launched by F (h_from), since both lose Δ;
  * expected shift: arrival(F/CK) − arrival(leaf-buffer input), with
    arrivals sampled before path enumeration;
  * allowed = min(s_cap − T, h_from − 20 ps, 80 ps). F is selected if the
    expected shift ≤ allowed.
* `scripts/re_launch_early.tcl` (POST_CTS hook, branch from R0a) moves the
  pins and measures the real shift from timing paths. It reverts a move that
  is too large or goes in the wrong direction; none was reverted.
* Optionally it first rebuilds RD_phys2 (`re_pre`), for the "combo" runs.

**The selection needed three attempts.** The first two missed launch flops,
and both shortfalls show up in the results.

| run | base / targets | how targets were found | moved flops |
|---|---|---|---|
| RE | RA | worst path per endpoint < 30 ps | `[20]` (it starts all 93 such endpoints) |
| RE_multi | RA | up to 50 paths per endpoint < 50 ps | `[20] [15] [31] [1] [0] [4]` |
| **RE_full** | RA | **each register's own launch slack < 50 ps** (`RE_MODE=launch`) | `[20] [15] [21] [1] [31] [0] [3] [4] [30]` (9) |
| RE_combo | RD_phys2 + | worst path per endpoint < 40 ps | `[20] [15] [1]` |

**Findings.**
1. **Launch-early is far more efficient than capture-delay here.** RE_full
   moves 9 CK pins, adds no cell, and costs +0.1 % clock power (+0.04 %
   total). It reaches WNS **+31.6 ps**, more than RD_phys2's +23.5 ps with
   36 buffers and +2.0 % clock power. The reason is the shape of the
   critical cone: a handful of instruction-register bits fan out to
   hundreds of register-file flops. One launch-side move helps thousands of
   paths at once. In the RE_multi scan, which looked at up to 50 paths per endpoint, `[20]` alone launched 5 676 of the near-critical paths found.
2. **The shift is real and nearly free in this topology.** After route, the
   9 moved flops are 35.7–42.0 ps earlier. The other 1 929 flops move by
   −1.8…+10.4 ps (median −0.2): the leaf nets lost a load, and the shared
   upstream nets gained up to 5 loads. That side effect is why the unmoved
   `[16]` dropped from +54.2 to +44.0 ps.
3. **The cost lands where predicted, and it is small.** Setup into the moved
   flops (fetch → instruction register) drops by 14–15 ps but keeps more
   than 0.10 ns. The worst hold paths into and from these flops are the DFFE
   enable-recirculation loops Q → D on the same flop, which shift with the
   flop, so hold is unchanged. Design hold WNS is unchanged, with 0 hold-fix
   cells.
4. **The selection rule matters as much as the move.** Two of the three
   attempts were limited by launch flops the selector did not see. Selecting
   by each register's **own launch slack** found them all. Path enumeration
   per endpoint does not, because one dominant startpoint fills the
   per-endpoint slots.
5. **The limit after one stage is the step size again.** RE_full is now
   limited by `[20]` itself (−14.3 + about 42 = +31.6 ps), because `[20]`
   started 24 ps behind the next bit and one buffer stage is worth only
   about 42 ps. Moving `[20]` two levels up would be the next step, if the
   setup into it allows: it had 0.103 ns left.
6. **Launch and capture combine.** RE_combo3 (RD_phys2's 36 capture buffers
   plus 10 launch moves) reaches **+48.2 ps**, the best result of the
   study. That is +24.7 ps over RD_phys2 for 10 wire changes, and
   +16.6 ps over RE_full for 36 buffers. It is now limited by `[15]`.

**Learned.**
* When the critical cone is "few launch → many capture", treat the launch
  side first. The capture-side rounds (E7/E8) were the expensive direction.
* Rank useful-skew candidates by their own launch/capture slack, not by
  enumerating paths per endpoint.

**Not done / open.**
* No two-level launch moves, and no automatic iteration of select → build →
  route.
* The side-effect load on shared upstream nets (up to +10 ps on other flops)
  is not part of the guard.
* As before, there is no fast corner to confirm hold.

## E10 — Moving `[20]` one more clock level up

**Question.** RE_full is limited by `instr_rdata_id_o[20]` itself (+31.6 ps)
after its CK was moved one level up. Does moving it a second level up help?

**Prediction (from RE_full post-route, before running).** `[20]` sits on
`clknet_4_4_0_clk` (8 sinks), driven by `clkbuf_4_4_0_clk` about 94 µm away.
The next net up is `clknet_0_clk`, the root trunk of the gated clock tree
(16 sinks, about 943 flops below it). The expected extra shift is 79 ps
(arrival 0.263 → 0.184 ns), because that level drives a long wire. Setup into
`[20]` had 102.5 ps, so it would fall to about +23 ps and become the worst
path. `re_select.tcl` rejected the move (expected shift 79 ps > allowed
67.5 ps). The balance point is about (102.5 − 31.6)/2 ≈ 35 ps of extra
shift.

**Method.** Both runs branch from R0a: RE_full's 9 moves, then a second
`re_launch_early.tcl` pass for `[20]` only (`re_rpt_name =
re_launch_early_pass2.rpt`; allowed relaxed to 95 ps on request).
* **RE_full2** (`scripts/re_full2.tcl`): `[20]` onto `clknet_0_clk`.
* **RE_full2b** (`scripts/re_full2b.tcl`): the same, then one `CLKBUF_X1`
  inserted in front of `[20]/CK` at the flop (fed from the trunk), so the
  extra shift is one level minus one buffer delay. At CTS stage the buffer
  added back 45.1 ps (`re_launch_early_pass2b.rpt`).

**Result** (post-route, OpenRCX).

**Findings.**
1. **A full second level overshoots, exactly as predicted.** `[20]` moves
   another 78.7 ps earlier. Its own launch paths go to +102 ps, but the

   instruction-register paths such as `[12]`/`[14]`/`[31]` → `[20]/D`, so

   by only −5.4 … +3.5 ps.
4. **The rule from E9 generalises.** A launch-side move must balance the slack
   of the paths the flop *launches* against the paths it *captures*. Whole
   clock levels are coarse: 42 ps for the first level, 79 ps for the second,
   because the higher net drives a longer wire. A level plus a buffer is a
   way to land in between.

**Learned.** `re_select.tcl`'s rejection (expected 79 ps > allowed 67.5 ps)
was right. Its estimate of the shift (79 ps expected, 78.7 ps realised) and of
the into-`[20]` slack (≈ +23 ps predicted, +24.6 ps measured) were both
accurate. The next lever is now `[15]` (+36.2 ps). It would need either a
second level or capture-side help (as in RE_combo3), each with the same
into/launch balance check.

## E11 — The same balance check for `[15]`

**Question.** RE_full2b (best launch-only result, +36.2 ps) is limited by
`instr_rdata_id_o[15]`. Does moving `[15]` a second clock level up, the same
check as E10, help further?

**Prediction (from RE_full2b post-route, before running).**
* `[15]` sits on `clknet_4_2_0_clk` (16 sinks; its driver is only about 8 µm
  away). The next net up is again the gated-tree root trunk `clknet_0_clk`,
  whose driver is about 47 µm away.
* Expected extra shift: 77.8 ps (arrival 0.2638 → 0.1861 ns).
* Unlike `[20]`, the paths *into* `[15]` have a lot of room (+128.3 ps), so
  `[15]` would end at about +114 ps launch / +50 ps into: still not the
  limiter. The balance point is (128.3 − 36.2)/2 ≈ 46 ps.
* `re_select.tcl` (RE_MODE=launch, RE_T=0.040) **accepted** the move this time
  (expected 77.8 ps ≤ allowed 80 ps), so no relaxation was needed.
* With `[15]` out of the way, WNS should be set by the next bits, `[16]`
  (+46.2) and `[21]` (+47.6), i.e. about +46 ps.
* Hold: `[15]`'s worst hold paths (from and into) were identical (0.154 ns),
  which points to its own enable loop Q → D, which moves with the flop.

**Method.** Both runs branch from R0a: RE_full2b's passes, then a third

* **RE_full3** (`scripts/re_full3.tcl`): `[15]` onto `clknet_0_clk`.
* **RE_full3b** (`scripts/re_full3b.tcl`): the same, then one `CLKBUF_X1` in
  front of `[15]`. The buffer insertion is now a reusable proc,

   gave +111.5 / +49.7 ps (predicted ≈ +114 / +50). The buffered version
   gave +75.7 / +94.9 ps. In both, `[15]` is no longer critical, and its
   hold is unchanged (the enable loop moves with it).
2. **But the WNS gain is small, for two reasons.**
   * *A real clock side effect.* Putting `[15]` on the root trunk adds one
     more load there. Every unmoved instruction-register bit's clock became
     3.4–5.4 ps later, while their register-file captures moved only about
     1 ps. That costs about 4 ps on all those paths.
   * *Data-path changes within the noise band.* In RE_full3 the remaining
     part dropped by a further 9–14 ps for `[12]`/`[25]`/`[29]`/`[27]`. In
     RE_full3b it is about 0 for most of them. The capture clocks did not
     move, so this is the data path. The GRT-stage repair had a different
     worst endpoint in each run (paths into `[15]` in RE_full3,
     `instr_addr_o[30]` in RE_full3b), and these 9–14 ps lie inside the
     ≈ 28 ps data-part noise band measured in E5. They cannot be attributed
     further.
3. **The buffered version is the better one again.** As with `[20]`, a level
   plus one `CLKBUF_X1` keeps both sides of the moved flop comfortable. The
   full level leaves the paths into `[15]` at +49.7 ps, right next to the new
   wall. RE_full3b reaches **+40.5 ps**, the best launch-side-only result:
   9 pin moves, two moved two levels, and 2 added cells, for +0.2 % clock
   power versus RA.
4. **The launch side is now flat.** The next bits are within a few ps of
   each other: `[12]` +40.5, `[16]` +45.6, `[21]` +49.1, `[31]` +51.6,
   `[14]` +51.6. Each further move adds load to the shared trunk (about
   +4 ps on everyone else) and re-rolls the routing noise. Further
   single-flop moves would return about as much as the noise.

**Bug found and fixed here.** `scripts/ir_launch_scan.tcl` took the first path
returned by `find_timing_paths -from <bit> -group_path_count 1`, which is the
worst path of the first path group, not of all groups. It now uses
`-sort_by_slack`. All 12 runs that use the scan were re-run. The only changes
were `[12]` in RE_full2b (+53.7 → +50.0 ps; its worst path goes to an output
port) and bit `[7]` (≈ +470 ps, irrelevant). E10 is corrected accordingly.

**Learned.** The balance check predicts the moved flop itself very well
(within about 3 ps in both E10 and E11). What it does not predict is the
side effect on other flops through the shared trunk, and the routing re-roll.
When the remaining launch bits are this close together, those two effects are
as large as the gain.

## E12 — OCV / timing derate with CRPR (limitation: "no OCV analysis")

**Question.** All earlier numbers use one typical corner with no on-chip
variation. Do the CTS / useful-skew gains survive OCV, and does useful skew
(which lengthens unshared clock paths) get penalized?

**Method.** STA only: no re-implementation. `scripts/e12_ocv.tcl` loads each
run's `6_final.odb` + SPEF, enables CRPR (`sta::set_crpr_enabled 1`, mode
`same_pin`), and reports setup/hold under:
* `none`: no derate. This reproduces the normal post-route numbers exactly
  (sanity check).
* `ocv5`: `set_timing_derate -late 1.05 / -early 0.95` on cell and net
  delays, clock and data paths.
* `ocv10`: late 1.10 / early 0.90.
* `fast5`: a crude **fast-corner proxy**, used for hold only. All cell delays
  and cell timing checks are ×0.80, then ocv5 on top. The platform has no
  fast library; real corners are in E17.

A second script compared ocv5 with CRPR on and off.

**Result** (setup WNS; Δ = gain over RA in the same scenario, ps).

| run | none WNS (Δ) | ocv5 WNS (Δ) | ocv10 WNS (Δ) | hold WNS none / ocv10 / fast5 (ns) |
|---|---|---|---|---|
| RA | −14.3 (0) | −151.5 (0) | −288.8 (0) | 0.0855 / 0.0609 / 0.0647 |
| RB_nocl | +4.3 (+18.6) | −131.1 (+20.4) | −266.6 (+22.2) | 0.0853 / 0.0544 / 0.0646 |
| RC_full | +16.4 (+30.7) | −119.2 (+32.3) | −254.8 (+34.0) | 0.0855 / 0.0492 / 0.0648 |
| RD_phys | +18.5 (+32.8) | −116.7 (+34.8) | −255.1 (+33.7) | 0.0856 / 0.0686 / 0.0648 |
| RD_phys2 | +23.5 (+37.8) | −114.6 (+36.9) | −252.6 (+36.2) | 0.0854 / 0.0667 / 0.0647 |
| RE_full | +31.6 (+45.9) | −103.4 (+48.1) | −238.3 (+50.5) | 0.0855 / 0.0615 / 0.0648 |
| RE_full3b | +40.5 (+54.8) | −92.9 (+58.6) | −226.4 (+62.4) | 0.0854 / 0.0702 / 0.0647 |
| RE_combo3 | +48.2 (+62.5) | −84.0 (+67.5) | −216.2 (+72.6) | 0.0854 / 0.0672 / 0.0647 |

CRPR on vs off under ocv5: setup WNS is **identical** in all five runs
checked (RA, RB_nocl, RD_phys2, RE_full3b, RE_combo3). Setup TNS gets
5–8 ns worse without CRPR, and hold WNS drops from about 0.081 to about
0.051 ns.

**Findings.**
1. **The ranking of all strategies survives OCV unchanged.** No gain shrinks
   by more than about 1.6 ps going from nominal to ±10 %.
2. **Useful skew is *not* penalized here, and launch-side gains even grow.**
   * Launch-early (RE_*) shortens the launch clock path, so less delay is
     multiplied by the late factor: +45.9 → +50.5 ps for RE_full, +62.5 →
     +72.6 ps for RE_combo3 at ±10 %.
   * Capture-side delay buffers sit in the capture clock path, which setup
     derates *early* (×0.95 / ×0.90). Their gain therefore shrinks by about
     the derate times the inserted delay: RD_phys2 +37.8 → +36.2 ps.
   * The penalty predicted in findings Q4 ("each useful-skew buffer adds an
     unshared stage") is real but only about 5–10 % of the skew amount, i.e.
     1–3 ps here.
3. **CRPR does not matter for the critical setup path, but matters a lot for
   hold.** The critical launch flop `[20]` sits in the gated clock subtree
   (`clk`), and the register-file captures sit in the ungated subtree
   (`clk_i_regs`). Their common clock path ends almost at the root, so
   there is no pessimism to remove. The worst hold paths are DFFE
   enable-recirculation loops, with the same flop as launch and capture
   and a fully common clock. CRPR removes all their pessimism (+30 ps).
4. **Hold stays clean in every derate scenario.** The lowest hold WNS is
   0.049 ns (RC_full, ocv10) and 0.065 ns under the fast-corner proxy. No run
   had a single hold violation. Whether this survives a *real* fast library
   is checked in E17.
5. Absolute numbers: with ±5 % OCV, 2.2 ns is far from closing (WNS −84 to
   −152 ps). A realistic sign-off period for this design and library would
   be about 2.35–2.45 ns, so the stress-period choice of E1 applies to the
   nominal analysis only.

**Learned.** OCV scales the clock-path *difference* between strategies by the
derate (±5–10 %), not by something larger, because these strategies change
only tens of ps of clock delay. CRPR is crucial for hold sign-off of
self-loop paths but irrelevant for this design's critical setup path,
because its launch and capture sit in different subtrees.

## E13 — Crosstalk proxy: coupling caps and Miller factor (limitation: "no crosstalk analysis")

**Question.** OpenSTA as used by ORFS has no signal-integrity engine, so every
earlier number ignores crosstalk delta delay. How much of the clock wiring is
coupling capacitance? Does NDR actually reduce it? Does the strategy ranking
survive a worst-case crosstalk bound?

**Method.** STA and SPEF only; no re-implementation.
1. **SPEF accounting** (`scripts/e13_spef_coupling.py`). Each `*D_NET` has
   grounded caps (`id node value`) and coupling caps (`id node1 node2 value`).
   OpenRCX lists every coupling cap in *both* nets' sections (checked on RA:
   189,223 of 189,223 pairs). Clock nets are found by walking from `clk_i`
   through combinational cells up to liberty clock pins
   (`scripts/e13_xtalk.tcl`, `E13_MODE=dump`). That gives 318 nets in RA,
   the same as the nets the ODB marks `CLOCK`. Useful-skew delay-buffer nets
   count as clock nets.
2. **Miller-factor STA** (`scripts/e13_run.sh`). A coupling cap is scaled by
   *k*: *k* = 0 means the aggressor switches the same way, *k* = 2 means it
   switches the opposite way. Scenarios:
   * `nom`: original SPEF.
   * `clk_x2`: clock-net coupling ×2 for early and late paths alike.
   * `clk_bound`: the max (late) parasitics have clock-net coupling ×2 and the
     min (early) parasitics have ×0. Every late path sees worst-case clock
     crosstalk and every early path best-case. For setup this means a slow
     launch clock and a fast capture clock; for hold, the reverse. CRPR is on.
   * `all_bound`: the same with *all* nets' coupling (data nets too).
3. **Tool bug found on the way.** `read_spef -coupling_reduction_factor`
   only works for 0 and 1. Factors 0.5, 1.5 and 2 give exactly the *k* = 1
   numbers (`results/e15_tool_issues.txt`). The cause is in OpenSTA's
   `parasitics/SpefReaderPvt.hh`: the member is declared
   `bool coupling_cap_factor_;`, so `cap * coupling_cap_factor_` multiplies
   by 1 for any nonzero factor. This holds on master as of 2026-11-04 and in
   the image. The workaround is to write SPEF copies with the coupling values
   already scaled. Rewriting at ×1 reproduces nominal exactly; ×2 changes
   timing as expected.

**Result 1: coupling share of wire capacitance** (`results/e13_coupling.csv`).

**Findings.**
1. **Clock nets are nearly as exposed as data nets.** About 40 % of clock
   wire cap is coupling, against 48 % for data nets. NDR full lowers the
   clock total only to 37.9 %. NDR goes on 9 of 318 clock nets. The other
   309 clock nets (lower tree levels and leaves), which hold 89 % of clock
   wire cap, never get it.
2. **On the trunk, NDR is effective, and the default `half` misses the most
   important net.** NDR full cuts trunk coupling from 53.7 to 21.7 fF
   (−60 %). The difference between `half` and `full` is `clk` and
   `clknet_0_clk`, the root of the *gated* subtree. That subtree holds the
   critical launch flop `[20]` (E12 finding 3), and its root net is the
   largest single clock net (about 62 fF, 55 % coupling).
3. **Because of that, NDR full halves the clock-crosstalk sensitivity.** With
   clock coupling ×2, mean latency rises +16 ps instead of +28 to +32 ps. In
   the bound, setup loses 35 ps instead of 60 to 66 ps.
   * RC_full's advantage over RA grows from +30.7 ps (nominal) to +55.1 ps
     (clk_bound).
   * RC_full (−18.9) overtakes RD_phys2 (−37.9) in the bound.
   * The E5 statement "only the clock half can be credited to NDR"
     undersold NDR: its main value, crosstalk immunity, is invisible to
     nominal STA.
4. **Useful-skew runs lose as much as the default** (−51 to −61 ps). They keep
   NDR `half` and add clock-net length (delay buffers, moved pins).
   RE_combo3 still ranks first in the bound (−3.0 ps) because it starts
   62 ps ahead. Combining it with NDR full is the obvious next step and was
   not run.
5. **Clustering-off and cluster-4 lose only about 30 ps.** RB_nocl has the
   lowest latency of all (274.9 ps), so there is less clock delay to
   perturb. RB_s4 has the *highest* latency (297.9 ps) and still loses only
   33 ps. Its smaller clusters mean shorter leaf nets, which may be the
   reason, but I did not check this per path.
6. **Hold stays clean in every bound.** The lowest hold WNS is 62.8 ps
   (RC_none, all_bound).
7. **The all-net bound is dominated by data-net coupling and swamps every CTS
   difference.** Setup WNS is −157 to −214 ps with about 1,560 violating
   endpoints. It assumes every aggressor of every net switches against its
   victim at the same time, with no timing windows. A real SI engine with
   timing windows and slew-dependent coupling would give much less. It is a
   bracket, not an estimate.

**Learned.** Nominal STA shows only the nominal-RC part of NDR's benefit and
none of its crosstalk benefit. A coupling-scaled SPEF is a cheap bound when
the STA has no SI engine. Check first that the option you rely on does
anything: here `-coupling_reduction_factor 2` silently did nothing.

## E15 — Root causes of the two OpenSTA anomalies (limitation: "worked around, not explained")

**Question.** Two OpenSTA behaviours had only been worked around:
* (a) the pin property `arrival_max_rise` on some register CK pins changed
  from 0.291 to 1.745 ns after `find_timing_paths` (E0);
* (b) a path object from `find_timing_paths` crashed OpenROAD when used after
  another query.

Why do these happen, and do they make any earlier number wrong?

**Method.** I read the OpenSTA source: master `deeff1d`, 2026-11-04. The image
reports OpenROAD version "unknown", so it may lag master, but both behaviours
reproduce in the image. I wrote minimal reproductions in
`scripts/e15_repro.tcl` on RA's post-route database (`E15_PART=A|B`; logs
`runs/RA/logs/.../e15_A.log` and `e15_B.log`). The key lines are collected
in `results/e15_tool_issues.txt`.

**Result (a): the arrival property.**
* Ibex's core clock gate is the latch `core_clock_gate_i.en_latch`
  (DLL_X1, transparent while the clock is low) plus AND2_X1 `_26153_`. Its
  A2 input is the clock and its A1 input is the latch Q. The AND2 drives
  `clk`, the gated subtree, which holds 943 of the 1,938 register clock pins.
  The other 995 are on `clk_i_regs`.
* Before any full search, `arrival_max_rise` at
  `cs_registers_i.mcountinhibit_q[0]/CK` is 0.296907 ns. After
  `sta::worst_slack_cmd max` it is 1.730380 ns.
* **All 943 gated-subtree pins change; none of the 995 `clk_i_regs` pins
  do.** `arrival_min_rise` stays at 0.2967 ns.
* `report_tag_arrivals` explains the change. After the full search the CK
  vertex carries four extra tags (1.73 / 1.75 ns), launched by
  `core_clock v` (the falling edge that opens the latch) and **without
  `(clock prop)`**, i.e. **data** tags.
* Control: `set_disable_timing` on the AND2 A1→ZN arc, then repeat. After
  the full search no CK pin changes by more than 1 ps.

The mechanism, from the source:
1. `Properties::pinArrival` calls `Sta::arrival(pin)`, which returns the max
   over **all** paths (tags) at the vertex, clock and data alike. Only
   generated-clock source paths are excluded (`search/Sta.cc`).
2. `Sta::arrival` first runs `Search::findArrivals(level)`, a **single**
   arrival pass. In that pass latch D→Q propagation is postponed
   (`postponeLatchDataOutputs` / `pending_arrivals_`, `search/Search.cc`), so
   the latch Q has no data arrival yet.
3. `find_timing_paths` and `worst_slack` run
   `findAllArrivals(thru_latches=true)`, which repeats passes until latch
   outputs settle. The latch Q data arrival then flows through AND2 A1→ZN
   into the whole gated clock tree as data tags.

So the property is order-dependent: it gives the clock latency before a full
search and the latest data arrival after one. Setup and hold checks are not
affected, because they use the clock tags. Only scripts that read pin
arrivals as "clock latency" are:
* `clock_report.tcl`
* `dump_ck_arrivals.tcl`
* `worst_paths.tcl`
* `rd_*`
* `re_select.tcl`
* `e13_xtalk.tcl`

All of them sample before any full search, so no reported number is
affected. For example, RA's reported insertion-delay maximum is 0.3122 ns,
not about 1.7 ns. `arrival_min_rise` is a safe alternative here, because
the gate's data arrives later than the clock.

**Result (b): dangling path objects.**
* `find_timing_paths` returns SWIG handles to `PathEnd` objects owned by the
  mode's `PathGroups` (`Mode::makePathGroups`).
* **Every** query starts with `Sta::searchPreamble()`, which calls
  `search_->deletePathGroups()`. The source comment reads: "Delete results
  from last findPathEnds because they point to filtered arrivals". That
  frees all `PathEnd`s.
* Reproduction:
  1. Hold the handle of the 2nd-worst path; its slack, −13.3 ps, reads fine.
  2. Run one `get_property … slack_max` on a pin.
  3. Read the handle again: `Signal 11 received` (SIGSEGV), and OpenROAD
     exits.
* Consequence: any pin slack or arrival query inside a `foreach` over
  `find_timing_paths` results leaves the rest of the list dangling. The safe
  pattern, used since the crash, is to extract every needed value from
  every path first and only then make other queries.

**Findings.**
1. Neither anomaly is a timing-engine error. (a) is a query-order-dependent
   property: a single-pass search with no latch iteration, combined with a
   max over clock *and* data tags. It shows up only on clock pins
   downstream of a latch-based clock gate. (b) is an ownership rule
   (results freed at the next query) that surfaces as a crash instead of an
   error.
2. Together with the `bool coupling_cap_factor_` bug from E13, these are
   three OpenSTA issues worth reporting upstream: (a) as a documentation or
   consistency issue, (b) as a usability issue (invalidate handles instead
   of crashing), and the coupling factor as a plain bug.
3. No number in this study changes. The affected scripts already sampled
   before path enumeration and extracted path values at once.

**Learned.** If a tool value changes depending on what you asked before,
look for lazy or partial evaluation (here a single pass versus iterated
latch passes). If an object crashes after a later call, look for ownership
(here results freed by the next query's preamble). Reading the source and
writing a minimal reproduction settled both faster than more workarounds
would have.

## E14 — Routing-noise distribution from 10 probes (limitation: "only 2 noise samples")

**Question.** E5 had two routing-only probes, a lower bound rather than a
distribution. How large is the noise really, and in particular the noise in
the *clock* part, which E5 put at ≤ 0.9 ps and which all CTS-knob
conclusions rely on?

**Method.** The same probe as E5 with 8 more values (`scripts/e14_noise.sh`).
Each probe branches from R0a with the default CTS, so the clock tree is
identical to RA. A `PRE_GLOBAL_ROUTE_TCL` hook sets the metal2–metal3
global-routing capacity adjustment to one of 0.44, 0.46, 0.47, 0.49, 0.51,
0.53, 0.54, 0.56 (RA = 0.50; E5 had 0.48 and 0.52). Each run is checked for
the hook's `FLW-0911` log line. Then the per-endpoint split of E7 over RA's
31 failing endpoints is computed (`scripts/e14_noise.py`; data
`results/e14_noise.csv`, plot `results/e14_noise.png`).

Fix found on the way: a branch run inherited the base run's
`ck_arrivals_final.csv` / `endpoint_slack_final.csv` from the copy, so a
probe could look complete before its own dumps existed. `run.sh` and
`run_big.sh` now delete these files when branching. No earlier number is
affected: every Phase 2 run had its dumps regenerated before analysis.

**Result** (Δ vs RA, ps; split = mean over the 31 endpoints).

| probe | adjustment | WNS (ps) | ΔWNS | Δslack | clock part | data part |
|---|---|---|---|---|---|---|
| N_gr44 | 0.44 | −18.8 | −4.5 | −5.22 | +0.04 | −5.26 |
| N_gr46 | 0.46 | −15.6 | −1.3 | −1.13 | −0.13 | −1.00 |
| N_gr47 | 0.47 | −9.3 | +5.0 | +4.90 | +2.50 | +2.40 |
| N_gr48 | 0.48 | −13.9 | +0.4 | +0.41 | +0.72 | −0.31 |
| N_gr49 | 0.49 | −14.3 | 0.0 | 0.00 | 0.00 | 0.00 |
| N_gr51 | 0.51 | +4.0 | +18.3 | +24.21 | −2.42 | +26.63 |
| N_gr52 | 0.52 | +6.3 | +20.6 | +26.82 | −0.91 | +27.74 |
| N_gr53 | 0.53 | +16.7 | **+31.0** | +30.79 | **+7.85** | +22.94 |
| N_gr54 | 0.54 | +5.2 | +19.5 | +19.89 | +2.79 | +17.11 |
| N_gr56 | 0.56 | −2.6 | +11.7 | +12.38 | +5.61 | +6.77 |

N_gr49 is bit-identical to RA (same clock report and endpoint dump), so
0.49 apparently rounds to the same track capacity as 0.50. That leaves **9
independent probes**:

| quantity | mean | sd | min | max |
|---|---|---|---|---|
| ΔWNS (ps) | +11.2 | 12.0 | −4.5 | +31.0 |
| clock part (ps) | +1.8 | 3.3 | −2.4 | +7.9 |
| data part (ps) | +10.8 | 12.9 | −5.3 | +27.7 |

In all three probes with a large clock part, the worst path to each of the
31 endpoints still starts at the same flop, so the clock part is real and
not a startpoint artifact. The CK arrivals themselves move. In N_gr53,
`[20]`'s CK arrival is 7.7 ps earlier, and the 1,938 CK pins move by −8.9
to +3.6 ps. In N_gr47 they move by −4.6 to −0.3 ps.

**Findings.**
1. **The clock-part noise floor is about 8 ps, not 1 ps.** Global route
   re-routes the clock nets as well, so a routing-only change moves clock
   latencies by several ps. E5's "≤ 0.9 ps" came from two samples that
   happened to be quiet.
2. **The CTS-knob conclusions, re-judged against an 8 ps / sd 3.3 ps clock
   floor:**
   * clustering off, clock part +18.9 ps: still clearly real, 2.4× the
     largest noise;
   * cluster size 4, +14.6 ps, and NDR full, +13.9 ps: real but only
     about 1.8× the largest noise (about 4σ);
   * NDR none, +4.6 ps: **inside the noise; no longer credited.**

   The useful-skew gains (+46 to +62 ps over RA) are far above the noise.
3. **WNS noise is large and one-sided relative to RA.** RA is a below-median
   draw: 4 of the 10 routing-only variants close timing at 2.2 ns, and the
   median ΔWNS is +5 ps. Any single-run WNS difference below about 30 ps
   between strategies could be routing luck. The per-endpoint split
   remains the right tool, but its clock part now needs about 8 ps of
   margin rather than 1 ps.
4. **The probe values are not a monotonic knob.** 0.44–0.49 stay near RA,
   0.51–0.54 all improve by 18–31 ps, and 0.56 by 12 ps. This is
   consistent with noise (a different detour set per capacity value), not
   with a trend that would justify tuning the adjustment.

**Learned.** Two samples can badly understate a noise floor. Here they did
for the one quantity, the clock part, that the conclusions leaned on. A
"clock-tree-only" comparison is never purely about the tree, because the
tree's wires are routed together with everything else.

## E16 — Automated select → build → route loop with a side-effect guard (limitation: "no automated iteration; shared-net load not in the guard")

**Question.** The useful-skew runs of E9–E11 were selected and built by
hand, one round at a time. Their guard looked only at the moved flop's own
shift. E11 measured the side effect that guard misses: every move onto a
shared upstream net makes that net's other sinks about 3.4–5.4 ps later.
Can a closed loop with a guard that includes that side effect find an
equal or better result without manual steps?

**Method.** Three scripts.
* `scripts/e16_select.tcl` runs STA on a *routed* result. It lists every
  register whose own launch slack is < 50 ps and whose CK net is driven by
  a buffer, worst first.
* `scripts/e16_hook.tcl` is the `POST_CTS_TCL` hook. It first re-applies
  the moves accepted so far; the CTS result is deterministic, so this
  rebuilds the previous tree exactly. Then, one candidate at a time, it
  moves the CK pin one buffer stage up, re-estimates parasitics, re-times
  the **whole design**, and keeps the move only if all three hold:
  * J = Σ min(0, slack − T_eff) improves;
  * setup WNS does not drop (tolerance 0.1 ps);
  * hold WNS stays ≥ 20 ps.

  Otherwise it reverts the move. Because every endpoint is re-timed, the
  extra load on the shared net counts against the move. A kept register is
  re-queued for another level (at most 3). Moves never cross the clock
  gate or an inverter. Post-CTS timing (placement RC) is about 55 ps more
  optimistic than post-route, so T_eff = 50 ps + (post-CTS WNS − post-route
  WNS of the same tree); without this shift J saw no endpoint below 50 ps
  after the first move.
* `scripts/e16_auto.sh` iterates: select on iteration k−1, build iteration
  k from R0a's placement, route + RCX, repeat.

**Result.**

| run | moves kept (registers / levels) | post-CTS WNS | post-route WNS | cells added | clock power |
|---|---|---|---|---|---|
| RA | – | +40.3 | −14.3 | 0 | 4.158 mW |
| **E16_1** | 5 / 6: `[20]`, `[1]`, `[31]`, `[0]` one level; `[15]` two levels | +78.7 | **+21.8** | 0 | 4.165 mW |
| E16_2 | none new (6 tries, all reverted) | +78.7 | +26.3 | 0 | 4.159 mW |
| RE_full (manual, E9) | 9 / 9 | – | +31.6 | 0 | 4.162 mW |
| RE_full3b (manual, E11) | 9 / 11 + 2 buffers | – | +40.5 | 2 | 4.167 mW |

Iteration 1 made 15 tries (`runs/E16_1/reports/.../e16_hook.rpt`). The
whole-design guard reverted 9 of them:
* `[21]`, `[3]`, `[4]` and `[30]` onto `clknet_4_2_0_clk`: each cost 0.7–1.3
  ps of post-CTS WNS, because the extra load delays `[15]`, which hangs
  from the same net. This is the side effect E11 measured.
* `[20]` a second level: WNS dropped 77.1 → 59.6 ps, the overshoot E10 found
  by hand.
* `[1]`, `[31]`, `[0]` a second level, and `[15]` a third.

Iteration 2 tried the 6 new candidates from E16_1's post-route timing and
kept none.

**Findings.**
1. **The loop runs unattended and converges in two iterations.** It finds
   the same family of moves as the manual work, including `[15]` two
   levels, and on its own rejects the `[20]` overshoot.
2. **But it ends about 10 ps below the manual RE_full.** On the critical
   endpoint `rf_reg[991]`, E16_1 − RE_full = −9.8 ps, split into:
   * clock −5.5 ps: `[20]`'s CK is 4.5 ps later. The guard accepted moving
     `[15]` a second level onto the root trunk `clknet_0_clk`, which
     `[20]`'s branch also hangs from. Post-CTS this looked like +1.6 ps of
     WNS; after routing it cost `[20]` about 4.5 ps.
   * data −4.3 ps: inside the routing noise of E14.

   So the guard catches the shared-net side effect, but it judges it with
   placement RC and misses the part that only appears after routing.
3. **A strict "no WNS loss" guard is conservative.** RE_full kept the four
   moves the guard rejected for a 1 ps post-CTS loss and came out ahead.
   A variant that allows each move to cost up to 2 ps (E16r,
   `E16_WNS_TOL=0.002`) tests this.
4. **Identical trees do not give identical results.** E16_2 kept no move,
   so its tree equals E16_1's, but it routed to +26.3 instead of +21.8 ps.
   The likely cause, not verified, is that a tried-and-reverted move
   disconnects and reconnects a CK pin, which re-orders the net's pins, and
   global route then builds different Steiner trees. The loop's first
   stopping rule (WNS only) counted this noise as progress and started a
   third iteration. I stopped it and changed `e16_auto.sh` to stop when an
   iteration keeps no new move. That change went into the auto-commit
   `5a90195` together with the E16 results.

**Learned.** Automating the loop is easy. The hard part is the model the
guard uses: post-CTS placement RC is optimistic and does not show the
routed side effects, and the routing noise (E14) is as large as the
decisions being made. A guard should either be evaluated on routed
parasitics or carry a margin of about the noise. A loop's stopping rule
must look at what changed, not only at the score.
